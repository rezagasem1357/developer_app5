# V15 اصلاح‌شده — cashier manager unified

این نسخه بر پایه V15 بدون خطای قرمز اصلاح شده است.

## اصلاحات اعمال‌شده
1. بارنامه: اطلاعات شرکت ارسال‌کننده و هزینه باربری در صفحه جدا و اختیاری؛ ورود کالا در صفحه بعد؛ تکمیل خودکار نام کالا با بارکد موجود در بانک؛ نمایش اسکرولی اقلام؛ جداکننده سه‌رقمی هزینه باربری.
2. ستاره «کالاهای جدید» فقط در پنل مدیریت نمایش داده می‌شود و در پنل صندوق‌دار حذف شده است.
3. ارتباط با شبکه: «دریافت بروزرسانی بانک» بزرگ و توپر و در ابتدای صفحه؛ «ارسال بانک» کوچک‌تر و فقط برای مدیر؛ دسترسی مدیریت رویدادهای روزشمار مشترک.
4. ابزار «ارسال پیام به تمام کاربران» برای مدیر اضافه شده است. پیام‌ها و پیام‌های آماده در `network_events` با نوع `broadcast_message` ارسال می‌شوند.
5. ابزار «گزارش عملکرد» برای مدیر اضافه شده و رویدادهای فروش، هزینه روزانه و بارنامه را از سرور با نام کاربری نشان می‌دهد.
6. تغییر قیمت مدیران با نوع `manager_price_change` به سرور ارسال و در تب «مدیران» گزارش می‌شود.

## نکته سرور
این نسخه برای پیام‌ها و عملکرد از جدول موجود `network_events` استفاده می‌کند؛ همان جدول باید اجازه INSERT/SELECT برای دستگاه‌های مجاز را طبق RLS فعلی پروژه داشته باشد.

اعلان پیام جدید هنگام دریافت/بررسی رویداد توسط برنامه ساخته می‌شود. برای اعلان واقعی Push در زمانی که برنامه کاملاً بسته است، نیاز به سرویس Push مانند FCM و تنظیمات سمت سرور است؛ این ZIP بدون اضافه‌کردن کلیدهای FCM، ادعای Push واقعی نمی‌کند.


## اصلاح ارتباط پیام و گزارش در این نسخه
- رویدادهای فاکتور فروش، هزینه روزانه، بارنامه و تغییر قیمت قبل از دریافت گزارش با صف همگام‌سازی شبکه ارسال/تلاش مجدد می‌شوند.
- دریافت گزارش مدیریت نیز ابتدا صف را با همان مسیر Sync شبکه تخلیه می‌کند و سپس رویدادهای سرور را می‌خواند.
- اعلان ساعت ۸:۳۰ دست‌نخورده باقی مانده است.
- یادآوری روزانه بررسی پیام‌های جدید ساعت ۱۵:۳۰ با نام کاربر و نام فروشگاه «فروشگاه فرهنگی مذهبی کریم اهل بیت (ع)» زمان‌بندی شده است.
- اگر جدول `network_events` قبلاً روی Supabase ساخته نشده، فایل `supabase/migration_network_events.sql` را در SQL Editor همان پروژه اجرا کنید؛ بدون این جدول، ارسال بانک ممکن است کار کند ولی پیام و گزارش عملکرد نمی‌توانند در سرور ذخیره شوند.

## اصلاح نهایی ارسال پیام و گزارش عملکرد (رفع خطای «برخی رویدادها برای ارسال بعدی باقی ماندند»)
- علت این خطا این بود که پیام‌ها و گزارش عملکرد از طریق جدول جداگانه `network_events` ارسال می‌شدند و اگر این جدول روی پروژه Supabase ساخته نشده باشد (یا RLS آن تنظیم نشده باشد)، هر ارسال با خطا مواجه و در صف باقی می‌ماند.
- در این نسخه، همان مکانیزمی که برای «ارسال/دریافت بانک اطلاعاتی» تست‌شده و همیشه کار کرده جایگزین شده است: پیام‌ها و رویدادهای گزارش عملکرد (هزینه روزانه، فاکتور فروش، بارنامه، تغییر قیمت) دیگر به جدول `network_events` نیاز ندارند و روی همان جدول `store_snapshots` (با یک شناسه مخصوص فید) ذخیره می‌شوند.
- در نتیجه اجرای فایل `supabase/migration_network_events.sql` یا وجود جدول `network_events` دیگر لازم نیست؛ فقط کافی است `supabase/schema.sql` (که جدول `store_snapshots` را می‌سازد) قبلاً روی پروژه Supabase اجرا شده باشد — همان چیزی که برای «ارسال/دریافت بانک» از قبل لازم بوده است.
- هیچ تغییری در ظاهر یا نحوه کار صفحات (ابزار ارسال پیام، صندوق پیام، گزارش عملکرد صندوق‌داران/مدیران) داده نشده؛ فقط لایه ارتباط با سرور در پشت صحنه اصلاح شده است.
